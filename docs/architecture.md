# Архітектура агента `build-engineer`

## Призначення

`build-engineer` — агент-оркестратор для TypeScript-проєкту (варіант 6).
Він допомагає підготувати проєкт до розробки, перевірити якість змін і
проаналізувати результати автоматизованого CI. Агент працює послідовно,
використовує вихід попереднього етапу як вхід наступного та повідомляє
користувачеві про результат кожної перевірки.

Агент не повинен вважати успішною команду, яка не була запущена, приховувати
помилки або продовжувати залежний етап після невдалої перевірки. Якщо потрібна
команда чи конфігурація відсутня, він має вказати це явно, а не підміняти
результат припущенням.

## Задачі агента

1. **Оцінити стан репозиторію.** Перевірити наявні файли, `package.json`,
   lock-файл, конфігурацію TypeScript, Vitest і GitHub Actions.
2. **Підготувати структуру.** Визначити відсутні частини початкового
   TypeScript-проєкту та створити або запропонувати їх у межах запиту.
3. **Перевірити зміни.** Запустити налаштовані npm scripts для збірки,
   типізації та тестів; зібрати коди завершення й діагностичний вивід.
4. **Перевірити CI.** Знайти workflows GitHub Actions і, за наявності доступу
   до GitHub CLI, переглянути запуски та їхні журнали.
5. **Підсумувати роботу.** Повідомити про змінені файли, запущені команди,
   їхні результати й невирішені проблеми.

## Skills і команди

### `project-scaffold`

Перевіряє початковий стан, узгоджує його з цільовою структурою TypeScript
проєкту та створює лише потрібні файли. Перед змінами враховує вже наявні
файли й не перезаписує користувацькі зміни без потреби.

**Вхід:** запит користувача та перелік наявних файлів.  
**Вихід:** перелік виявлених прогалин і створених або змінених файлів.

### `build-and-test`

Запускає доступні npm scripts і передає оркестратору повний статус кожної
команди.

**Цільові команди:**

- `npm ci` — встановлення залежностей за lock-файлом; застосовувати лише коли
  lock-файл існує.
- `npm run build` — збірка проєкту.
- `npm test -- --run` — одноразовий запуск Vitest через npm test script.
- `npm run typecheck` — перевірка типів, якщо відповідний script визначений.
- `npm run lint` — lint-перевірка, якщо відповідний script визначений.

Перед запуском агент перевіряє наявність відповідного script у `package.json`.
Відсутній script фіксується як недоступна перевірка, а не як успіх.

**Вхід:** змінені файли та доступні npm scripts.  
**Вихід:** команда, код завершення й релевантний вивід для кожної перевірки.

### `github-actions`

Перевіряє workflow-файли в `.github/workflows/` та, коли GitHub CLI встановлено
і авторизовано, дає змогу переглянути стан CI.

**Команди GitHub CLI:**

- `gh workflow list`
- `gh run list`
- `gh run view <run-id> --log`

Skill передає оркестратору знайдені workflows, стан запусків і повідомлення з
журналів. Запуск або повторний запуск workflow не виконується без відповідної
потреби й дозволу користувача.

**Вхід:** workflow-файли та доступність GitHub CLI.  
**Вихід:** перелік workflow, статус запуску або чіткий опис проблеми доступу.

## Оркестрація та передавання даних

1. Оркестратор отримує запит і формує контекст: ціль задачі, стан репозиторію,
   наявні конфігурації та обмеження користувача.
2. `project-scaffold` отримує контекст і повертає перелік змін та оновлений
   стан структури.
3. Якщо запит передбачає перевірки, оркестратор передає змінені файли й
   `package.json` до `build-and-test`. Skill повертає структуровані результати:
   назву команди, статус завершення та вивід.
4. Якщо запит стосується CI або потрібно перевірити GitHub Actions,
   `github-actions` отримує контекст workflows та результати попередніх
   перевірок і повертає стан CI та діагностику.
5. Оркестратор об'єднує результати skills і формує підсумок із переліком
   виконаних дій, перевірок і подальших кроків.

Між етапами передаються лише дані, потрібні наступному етапу: запит і контекст
репозиторію, перелік змін, конфігурація команд, результати запусків і журнали
помилок. Результат кожної перевірки має бути пов'язаний із конкретною
командою; відсутність результату не трактується як успішне виконання.

## Обробка помилок

- Якщо команда завершується ненульовим кодом, оркестратор зберігає її вивід,
  позначає відповідний етап як невдалий і включає причину до підсумку.
- Якщо збірка не пройшла, залежні перевірки, для яких потрібен її результат,
  не оголошуються успішними. Незалежні діагностичні перевірки можуть бути
  виконані, якщо це безпечно й доречно.
- Якщо npm script, lock-файл, workflow, GitHub CLI або авторизація відсутні,
  агент повідомляє, яка саме передумова недоступна, і не підставляє
  вигаданий результат.
- Якщо GitHub CLI повертає помилку чи недоступний сервіс, помилка передається
  в підсумок разом із виконаною командою.
- Після помилки агент зупиняє лише залежну частину процесу; він може завершити
  незалежні етапи й надати користувачеві повний звіт про часткове виконання.

## Запуск

Поточний локальний цикл запуску:

1. Установити зафіксовані залежності командою `npm ci`.
2. Запустити збірку `npm run build` і Vitest тести `npm test`.
3. Для локального запуску CI wrapper на Linux/macOS використати
   `bash scripts/ci.sh`, а у Windows — `scripts\ci.bat`.
4. У VS Code обрати агента `build-engineer` і надати задачу природною мовою.

GitHub Actions виконує обидва runner scripts на матриці
`ubuntu-latest`, `windows-latest` і `macos-latest`. Результати локальних
перевірок не замінюють перевірку всіх віддалених runners.
